# reviews（项目书评审）

> 项目书同行评审。**模块说明在 [`reviews/README.md`](../../reviews/README.md)**——四张表、
> 状态机、三道唯一约束、锁序与事务边界、失败模式、测试与已知限制全在那里。它是全平台最复杂的一块，
> 值得从头读到尾。
>
> 这一篇只留**跨模块口径与由来**。

**什么时候看**：碰评审规则的边界（它和项目组、通知、资格怎么咬合），或想知道某条规则当初为什么这么定。

---

## 跨模块口径

- **项目书只存一份**在 `ProjectGroup.proposal`（归 `projects`），评审侧任何表都不复制它；只有批注版与归档版是 reviews 自己的文件。
- **消息的写入与撤回归 `notices`**（`notify_preliminary_task` / `notify_review_task` / `clear_review_task_messages` / `notify_review_result`），reviews 只调用；任务消息跟着任务生命周期走，历史归评审页。
- **资格判定归本模块**：`projects` 与 `accounts` 需要问「他是不是评审人」时，在**函数体内**局部 import `reviews.permissions`。**但有一条加载期的反向依赖**：`accounts/admin.py` 在模块级 `from reviews import lifecycle`（两个资格名册要取 `STAGE_*` 常量）——这是全平台唯一一条反向加载期依赖，要动它先确认不成环。
- **状态口径只能问 `lifecycle`**：`OPEN_STATUSES` / `stage_is_open()` / `transition()` 是唯一判据；别处改写 `status == "pending"` 会漏掉「初审中」。
- **匿名口径落在三处**（页面／落盘名／下载头）——落实方式与改动注意见 [`reviews/README.md`](../../reviews/README.md) §5。任何一处漏掉，都能从存储层或页面反向认出评审人，而匿名是评审人敢说真话的前提。
- **建组申请的待办摆在本模块的队列页**，但模型与处理都归 `projects`（`reviews.panels` 只负责摆上去）。

## 由来

- **为什么初审是「关卡」而不是「评审团」**：一轮只设 1 名初审人，给的是理由（意见）而不是稿子（没有批注版）——没准备好的项目书不该占用评审人的时间。
- **为什么提交时就做容量预检**：不预检会开出一轮谁也推进不了的送审——联系人被单轮次约束挡着、初审人也通不过，只能等管理员补资格或超级评审收场。
- **为什么接单开关是字段而不是一张表**：它替换掉的是「请假窗口」（两个时间点 + 事由 + 到点自动恢复）。窗口要表达的其实是「这个人现在收不收新任务」，用时间区间去逼近它，代价是一张表、一套登记/取消服务、一条后台屏和一个「到点自动恢复」的隐含承诺；换成两个布尔字段之后，恢复就是本人按一下，抽人与改派各自少一处时间比较。**代价是丢掉了「未来某段时间不接单」的预约能力**——现在只能到时自己关（当时判断：这个能力没人真用，而它撑着上面那一整套机器）。
- **为什么一票敲定不走 `_settle_submission`**：那条汇总回答的是「是不是每个评审人都通过了」，会把某个普通评审人先前的「需修改」顶回去——而那正是这条路径要做的决定。
- **归档口径（以代码为准）**：一票敲定通过时，归档只收「`completed` 且 `approve`」的批注版；此前判过「需修改」的评审人即便上传了批注版也不进归档。（本文旧版本写的是「会一并收走此前上传的批注版」，比代码宽，已按代码更正。）
- **待办数字**：`pending_task_summary()` 的调用方是成员中心的**接单开关面板**（把「手上还有几件没交」摆在开关旁边，那条「有未完成任务就关不掉」的规则才是可预期的）；队列页的数字仍由 `queue_context` 分档后自己数。
