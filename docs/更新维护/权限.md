# 权限

> 谁能做什么：权限矩阵、对象级权限，以及审计判定时该往哪儿找。
>
> **判定的实现**在各 app 的 `permissions.py`（以及 `notices/visibility.py` 这类单点模块）；
> 这份文件是**回答「这个功能谁能用」的第一落点**，也是各模块判定口径的对照表。

**什么时候看**：加一种身份、改一处判定，或回答「这个功能谁能用」。

## 角色

➥ **各角色的词义归 [`../术语表.md`](../术语表.md)（唯一主）**，包括身份那两种作用域各由谁产生、
管理方式差在哪。这里只补一句：**作用域决定了后台给不给分配入口**，判据不在本文件，在
`core/roles.py` 的目录条目与各 app 的 `permissions`。

### 判定不止一种写法——审计时别只 grep `require(`

新代码都按「判定写在 `permissions.py`、门槛走 `core.permissions.require`」写，但**另有若干处历史写法**，
效果相同、样板重复：

- 视图自己 `logger.warning(...)` + `raise PermissionDenied`（例如 `projects:group_materials_download`
  与 `reviews:complete`——**这两处越权不留日志**）；
- `discussion` 的建／删板块判定**直接读 `is_superuser`**（它是全站唯一把超级用户当作独立资格的
  地方），且页面按钮与视图判定必须同源；
- 借用记录的可见范围**不是判定函数**，是在查询里收窄的（`equipment` 整个 app 没有 `permissions.py`）。

所以审计权限时**别只 grep `require(`**，那会漏掉上面这几处。

## 对象级权限（唯一的复杂度点）

Django 原生支持「组级」权限，**对象级**要自己写。项目组相关的判定都收敛在
`projects/permissions.py` 一处，别的模块复用——**具体有哪些函数、各自算什么，读那个文件**
（每个函数都带 docstring）。这里只记两条从代码里看不出来的：

- **`can_view_group` 是几支的并集**（staff ／该组成员 ／本轮初审人 ／被分配评审人 ／该组有进行中
  轮次时的超级评审）：改它时**不许提前 `return`**，否则同时具备多种资格的账号会丢掉任务带来的
  可见性。**它管详情与三处受保护件取件；列表的可见范围是另一支**（`groups_visible_to`，登录即全部），
  别把两者混为一谈——放宽列表不等于放宽取件。
- **有几处判定根本不在 `permissions.py` 里**：见上面「判定不止一种写法」。
