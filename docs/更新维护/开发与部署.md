## 1. 环境

### 1.1 本地

数据库**固定 PostgreSQL**（Django 5.2 要求 ≥14），连接参数写在根目录 `env.local.sh`：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.txt

source env.local.sh          # 必须：不加载会因缺少库名/账号/密码连接失败
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
.venv/bin/python manage.py runserver
```

访问：首页 `/`、成员登录 `/login/`、管理后台 `/admin/`。**SQLite 已移除**——任何
`migrate` / `test` / `runserver` 前都要先 `source env.local.sh`；看到
`fe_sendauth: no password supplied` 之类错误即是忘了 source。

**一个数据库扩展**：迁移 `content.0004_pg_trgm` 会 `CREATE EXTENSION pg_trgm`
（获奖判重用它算相似度）。它自 PostgreSQL 13 起是 trusted 扩展，**库的属主即可创建**，
本地与 `install.sh` 建的库都满足；权限被收走时用超级用户执行一次
`CREATE EXTENSION pg_trgm;` 再重跑迁移。

### 1.2 生产

```bash
sudo apt update
sudo apt install nginx postgresql python3 python3-venv python3-pip git gettext
sudo useradd -m -s /bin/bash club      # 运行应用与备份的系统用户，脚本要求它真实存在
```

> **版本以锁文件与构建文件为准**，这里只写「需要什么」。`requirements.txt` /
> `requirements-prod.txt` 是 `pip-compile --generate-hashes` 生成的锁文件（精确版本 +
> 全部平台的哈希），安装一律带 `--require-hashes`——依赖被篡改或供应链投毒会当场失败，
> 而不是安静地装上一个被换过的包。改依赖时改 `.in` 再重新编译：

```bash
.venv/bin/pip install pip-tools
.venv/bin/pip-compile --generate-hashes --output-file requirements.txt requirements.in
.venv/bin/pip-compile --generate-hashes --output-file requirements-prod.txt requirements-prod.in
```

**升级依赖后要留意两件事**：① **glibc 版本**——Pillow 12.x 的 Linux 轮子改用
`manylinux_2_28` 标签（要求 glibc ≥ 2.28），换更老的系统会退回源码编译；② **跑一遍全量
测试**，尤其图片解压炸弹那几条（防护依赖 Pillow 的 `DecompressionBombError` 与
`MAX_IMAGE_PIXELS`，主版本升级必须确认这两个还在、行为没变）。

### 1.4 代码内固定配置

➥ 这些不走环境变量，改它们要动代码。

| 配置 | 值 | 作用 |
|---|---|---|
| `MEDIA_URL` / `MEDIA_ROOT` | `/media/` / `mediafiles/` | **公开**媒体（媒体库配图），Nginx 直出 |
| `PRIVATE_MEDIA_ROOT` | `protected_media/` | **受保护**上传件，只能经视图取 |
| `AXES_FAILURE_LIMIT` / `AXES_LOCKOUT_PARAMETERS` | `10` / 账号与 IP 各算 | 登录失败锁定 |
| `FILE_UPLOAD_MAX_MEMORY_SIZE` / `DATA_UPLOAD_MAX_MEMORY_SIZE` | `5 MB` | 显式写死，不让它随 Django 版本漂 |
| `AUTH_USER_MODEL` | `accounts.User` | 已迁移，**不可中途更换** |
| `AUTH_PASSWORD_VALIDATORS` | 相似度／最小长度／常见密码／纯数字 | 密码强度 |
| `INSTALLED_APPS` 里的 `django.contrib.postgres` | — | 只为 `pg_trgm` 相似度；无模型、无迁移 |

**用户可填文本的长度上限**：成员能自由填写的长文本都有上限（评审意见 5000、送审说明 5000、
入组申请理由 2000、项目组描述 2000、组介绍 2000、报名备注 2000、借用备注 1000）。没有上限的
文本字段是一条**廉价的写入放大路径**——一次请求就能塞进很大的内容，把库撑大、把后台列表与页面
渲染拖慢。表单与模型两边都写：表单先给出友好报错，模型兜住后台表单与脚本写入。
`core/tests/test_upload_validation.py` 会逐项核对这张口径表。管理员才能写的正文
（通知正文、公开内容页、竞赛说明等）不设上限——威胁面小得多。

**媒体上传限制**：图片 `jpg/jpeg/png/webp/gif` ≤10 MB（Pillow 解码校验）；视频 `mp4`
（查 `ftyp`）／`webm`（查 EBML 头）≤500 MB。项目书与批注版 `doc/docx/pdf` ≤20 MB
（扩展名 + 文件头签名，复用同一校验器）。扩展名、大小、MIME、签名任一不符即拒绝。

## 2. 构建 / 测试 / 运行

先 `source env.local.sh`，命令一律走项目 venv：

```bash
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run   # 预期 No changes detected
.venv/bin/python manage.py test                               # 全量，用测试库
.venv/bin/python manage.py runserver 127.0.0.1:8021 --noreload
.venv/bin/python manage.py collectstatic --noinput
.venv/bin/python -m compileall -q config accounts notices discussion content media \
    projects competitions reviews equipment core manage.py
```

**验收 = 前三项全绿**（`check` + `makemigrations --check --dry-run` + `test`）。这三条与
[`../../CLAUDE.md`](../../CLAUDE.md) §5 是同一份事实，**改这里必须同步改那里**。

其他常用：生成／应用迁移用 `makemigrations` / `migrate`，看状态用 `showmigrations`，
生产安全自检用 `check --deploy`（本地有警告属正常）。单模块 `manage.py test reviews projects`，
单条 `manage.py test accounts.tests.MemberAuthenticationAcceptanceTests`。

**测试的几件事**：

- `reviews` 的用例最多，因此按功能拆成 `reviews/tests/` 包，一个模块一个主题。共用件只有两处：
  `factories.py`（造对象）与 `base.py`（`ReviewTestCase`：临时 MEDIA_ROOT + 推进轮次的动作）。
  **夹具（谁是评审人、各有几名）刻意留在各个类自己的 `setUp`**：送审类型决定名额，而名额是
  「恰好抽到谁」这类断言的前提，由基类统一发放夹具会让这些断言随候选人数变化而时灵时不灵。
- **测试跑得快是配置出来的，不是碰巧**：`manage.py test` 时 `config.settings` 会把
  `PASSWORD_HASHERS` 换成 MD5。判定只认命令行里的 `test`（`config.settings.running_tests()`），
  生产进程不经过它、口令仍是 PBKDF2。`config/tests.py` 钉住这条判定不外溢，**改它之前先看那三条测试**。
- **CI**（`.github/workflows/ci.yml`）在 PR 上跑三道门：`check --deploy` 门禁、全部测试、
  `pip-audit` 依赖漏洞扫描。门禁那一步与 `deploy.sh` 里那道同一口径，只是提前到合并前。

**一个数据库扩展**：见 §1.1。

## 3. 代码约定

### 3.1 注释怎么写

代码里的注释是**中文自由式**，只服务一条原则：**写代码看不出来的东西**——为什么这么做、
边界在哪、什么时候会失败。签名里读得出来的（参数名、返回什么）不写；「先取对象、再校验」
这种把代码念一遍的也不写。

| 位置 | 写什么 |
|---|---|
| 模块 docstring | 这个模块负责什么、**为什么把它单独拆出来** |
| 公开函数 | 语义、前置条件、**失败模式**：抛哪个领域异常、视图会把它翻译成什么；拒绝时是 403 还是 404 |
| 行内注释 | 只有一种：**为什么非得这么写**。反直觉的写法、必须维持的顺序、看起来多余却不能删的那一行 |

**失败模式是当前最缺的一条。**读代码时最费劲的不是「它做了什么」，而是「什么情况下它会
拒绝我、以什么形式拒绝」。服务层抛领域异常、视图翻成 `messages` 或 403/404——新写服务函数时
把这条写进 docstring。

几条具体的：**并发与锁要写明**（靠行锁保证正确性时，docstring 里写清锁的是哪一行、为什么非锁
不可——这是最容易在重构时被当作冗余删掉的一行）；**不写会过期的数字**（条数、行数、耗时写在
提交信息里）；**交叉引用用 Sphinx 式**（`:func:` / `:class:`，与既有代码一致；项目不接文档
生成器，它只是给人跳转用）；**不复述模型字段**（字段含义写在 `models.py` 的定义处）。

### 3.2 样式与模板约定

页面外观集中在 `static/css/app.css`，模板不写行内样式、不写 `<style>`、不写内联
`<script>`（页面脚本放 `static/js/` 并由模板引用）。

- **令牌**：颜色、字体、宽度都取自文件顶部的 `:root` 变量；调整配色只改这一处。
- **骨架类**：`topbar` / `pagehead`+`path` / `spec` / `panel`+`panel-head`+`panel-body` / `frame` / `split`。
- **组件类**：`btn`（`-primary`/`-danger`/`-sm`/`-block`）、`chip`（`-pin`/`-ok`/`-warn`/`-off`/`-on`）、`table-wrap`、`field`、`dl`、`prose`、`entries`/`entry`、`todo`、`queue`/`qitem`、`rounds`、`empty`、`flash`。
- **字体**：只用系统字体栈，不加载外部字体；等宽字只用于编号、日期、文件规格这类真值。
- **动效**：`.reveal` 只在页面载入时编排一次淡入，并遵守 `prefers-reduced-motion`；不要给每个区块加逐条动画。
- **折叠的判据在 CSS**：长帖折叠的高度只写在 CSS 类里，脚本不重复那个数字——它先套类、再问浏览器有没有真的溢出。

表单控件由元素选择器统一着色，新增字段无需加 class。页面专属脚本放 `static/js/`。

### 3.3 中英双语与翻译文件

**中文是源语言**：模板与代码里写的 msgid 本身就是中文，所以中文不需要翻译文件；英文译文
集中在 `locale/en/LC_MESSAGES/django.po`。**地址即语言**：中文沿用不带前缀的地址，英文走
`/en/`（`i18n_patterns(prefix_default_language=False)`），与浏览器语言、Cookie 无关；
**后台 `/admin/` 不在范围内**（刻意留在 `i18n_patterns` 之外，固定中文）。只翻译界面——
通知正文、竞赛说明、项目组简介等由人录入的内容原样显示。

写新文案时：

- **不要拼接句子**——`f"{label}任务"` 拼出来的话没法翻译，一律用 `_("%(label)s任务") % {...}` 占位；模板用 `{% translate %}` / `{% blocktranslate %}`（短句单行，多行块加 `trimmed`）。
- **惰性译文不要在导入时插值**：`gettext_lazy` 拿到的是代理，`_("…") % {...}` 会在**写这行代码的那一刻**求值，语言就此定型，之后切英文也不会变。要插值用 `format_lazy`（`django.utils.text`）。`core/tests/test_interface_translation.py` 里有一条静态检查专门扫这种写法。
- **带数量的文案要分单复数**：模板用 `{% blocktranslate count %}`，Python 用 `ngettext()`；中文单复数同形，所以单数那一半直接写死 1。
- **给成员用的 `ModelForm` 要在 `Meta.labels` 写一遍标签**：默认拿模型的 `verbose_name`，而模型上的中文是写给后台的、不进 `.po`，照搬过来就是英文表单上冒出中文标签。

改完文案后：

```bash
.venv/bin/python manage.py makemessages -l en --no-obsolete   # 提取新增/改动的文案
# 编辑 locale/en/LC_MESSAGES/django.po，填入 msgstr
.venv/bin/python manage.py compilemessages -l en              # 本地预览英文用
```

`.mo` 是编译产物**不进版本库**：服务器上由 `deploy.sh` / `install.sh` 按当版 `.po` 现编，
线上英文因此不可能与 `.po` 漂移；服务器缺 `gettext` 时部署当场失败，而不是让英文静默退回中文。
**漏译与漏提取才是真正会静默的坑**（页面上英文夹着中文、没有任何报错），所以
`core/tests/test_interface_translation.py` 把它们挡在验收之前：标了翻译的文案必须都在 `.po` 里、
译文非空、占位符与原文一致、复数条目两条齐全。

不在双语范围内的部分：后台界面与后台表单、只用于后台的模型 `verbose_name`、
`core/templatetags/files.py` 的文件类型角标。

## 4. 部署

### 4.1 第一步：一次性的安装

`deploy/install.sh` 依次完成：**环境检测 → 配置检测 → 建库／建角色 → migrate →
collectstatic → 建超管 → 注册 systemd 服务与备份 timer → 配置 Nginx → 健康检查**。

原则：**检测到依赖或配置不符合就中止**，绝不自动下载安装任何软件——缺什么、怎么补，
提示都会写明。重复运行安全（建库／建超管幂等）。

```bash
sudo mkdir -p /opt/702platform && sudo chown club:club /opt/702platform
sudo -iu club
cd /opt/702platform
git clone <仓库地址> .
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install --require-hashes -r requirements.txt -r requirements-prod.txt

cp deploy/env.template env.sh && chmod 600 env.sh && vi env.sh    # 替换全部 <尖括号>
sudo ./deploy/install.sh
```

**必须替换的项**：`DJANGO_SECRET_KEY`（`openssl rand -base64 36`）、`DJANGO_ALLOWED_HOSTS`、
`DJANGO_DB_NAME` / `_USER` / `_PASSWORD`、`DJANGO_SUPERUSER_USERNAME` / `_EMAIL` / `_PASSWORD`、
`DEPLOY_DOMAIN` / `DEPLOY_PUBLIC_IP`（Nginx `server_name` 两项都写，健康检查的 `Host` 头）、
`DEPLOY_SYSTEM_USER`。`install.sh` 与 `deploy.sh` 的占位符校验（`<尖括号>`）是硬门禁，
不会放行「复制模板后忘了替换」。

**部署形态**：单台服务器、单进程 gunicorn（systemd `club702.service`）、PostgreSQL 在本机、
Nginx 作反代与静态服务；**不支持**多机／对象存储／灰度发布（要换形态时媒体层是留好的接缝，
见 §7.1）。数据在 PostgreSQL，受保护上传件在应用目录下的 `protected_media/`，配置在 `env.sh`。

### 4.2 更新

```bash
# 开发机打 tag
git tag -a v1.0.1 -m "发布说明" && git push <remote> main --tags

# 服务器一条命令（<部署用户> = env.sh 里的 DEPLOY_SYSTEM_USER）
cd ~/applications/702platform
./deploy/deploy.sh v1.0.1
```

`deploy.sh` 的顺序：**备份库与媒体 → `chmod 600 env.sh` → checkout tag → 升级依赖 →
`check --deploy` 门禁 → `mkdir -p protected_media` → `migrate` + `collectstatic` +
`compilemessages` → 重启 → 健康检查（先打 Nginx、再退回直连 gunicorn）**。任何一步失败即中止。

其中**门禁那一步会拦下**「`DEBUG` 还开着」「Cookie 没带 Secure」「`SECRET_KEY` 还是源码默认值」
这类不会让站点起不来、只会让它安静地不安全的问题。版本号命名 `v主.次.修订`（修订=修复，
次=新功能，主=不兼容）。

**健康检查要看清验到了哪一层**：它通过后会打印 `经 Nginx（…）` 或 `直连 gunicorn（…）`。
**两种结果的含义不同**——成员走的是 Nginx 这条路，只验到直连等于**没验到成员看到的那一层**。
看到「直连」就要去查 Nginx（`nginx -t`、`systemctl status nginx`、`journalctl -u nginx -n 50`），
别把它当成绿灯。

手工复核两条：

```bash
curl -i -H 'Host: <DEPLOY_DOMAIN>' http://127.0.0.1:80/   # 经本机 Nginx
curl -i http://127.0.0.1:8000/                            # 直连，期望 200 且响应头含 X-Request-ID
```

再按业务流程走一遍：公开首页 → 管理员建成员账号 → 成员首次登录强制改密 → 内部通知按组可见 →
项目组／联系人竞赛报名 → 设备借还 → `/admin/core/auditlog/` 只读审计。

> **`/etc` 下的配置归 `install.sh` 管**：改了 `deploy/` 里的 Nginx／systemd 模板要
> 「先 `deploy.sh` 再 `install.sh`」，并**读回线上文件核对**；`deploy.sh` 只检查、不修。

### 4.3 HTTPS

证书走 Let's Encrypt 的 **IP 地址证书**（不需要域名、也不需要备案），由独立 venv 里的
certbot 签发与续期；`install.sh` 发现还没签证书时会把签发命令打出来。证书是
**shortlived profile，只有几天有效期**（不是 90 天），所以续期 timer 一天跑两次是硬需求：
certbot 在剩余不足寿命 1/3 时才动手续，一天两次意味着到期前有若干次尝试机会。

**这台机器上可能有两个 certbot，手动碰证书时最容易踩这个坑。**发行版仓库那个
（`/usr/bin/certbot`）认不出 IP 证书，`renew` 会报
`At least one of domains or ipaddrs parameter need to be not empty`——**这是假故障**，
真正负责续期的那个（`env.sh` 的 `CERTBOT_BIN`，要求 ≥ 5.4）一切正常。分辨方法：输出里
`Simulating renewal of an existing certificate for` 后面**空着**就是跑错了二进制。所以这类
命令一律写全路径。

**四个开关要一起设**（`env.sh` 里显式写死的值会**覆盖**代码默认值，所以升级时必须改文件）：

```bash
DJANGO_SESSION_COOKIE_SECURE=1     # Cookie 上的 Secure 属性由它直接决定
DJANGO_CSRF_COOKIE_SECURE=1
DJANGO_PROXY_SSL_HEADER=1          # 让 Django 知道请求其实是 https
DJANGO_CSRF_TRUSTED_ORIGINS=https://<域名>,https://<公网IP>   # 成员实际访问的每个入口都要写
```

前三项改完才能通过 `check --deploy` 门禁（否则以 `security.W012` / `W016` 中止部署——有意
设计：宁可发布失败，也不让站点安静地不安全）。`DJANGO_SECURE_SSL_REDIRECT` 与
`DJANGO_SECURE_HSTS_SECONDS` **继续留空或 0**。

**第四项不是可选项，漏填的后果是表单提交 403。**Django 每次 POST 都会把浏览器发来的
`Origin` 头与「`request.is_secure()` 判断出的协议 + Host」比对，对不上就拒绝。生产上 TLS 由
Nginx 终结、Django 自己看不出是 https（除非开 `PROXY_SSL_HEADER`），于是它期望 `http://…`
而浏览器发的是 `https://…`，必然对不上。**注意这一项不在 `check --deploy` 的检查项里**：
门禁拦不下它，症状要等成员提交表单时才出现，所以照着模板逐字确认，别凭印象。

`SESSION_COOKIE_SECURE` 与 `PROXY_SSL_HEADER` 是两件事，别搞混：前者**直接决定** Cookie 带不带
`Secure`；后者管的是让 Django 知道「这个请求其实是 https」，影响 `request.is_secure()`、
CSRF 的 Origin 校验、以及 `SECURE_SSL_REDIRECT` 会不会误判成死循环。

**顺序**：① 先换证书本身、确认 HTTPS 正常 → ② 设受信来源 → ③ 确认没有 http 访问需求后再开
整站跳转（`DJANGO_SECURE_SSL_REDIRECT=1`）→ ④ HSTS **最后**再考虑，且先给一个很短的窗口
（`DJANGO_SECURE_HSTS_SECONDS=60`）试水。**加长到一年之前想清楚证书续期是不是自动的**——
证书一断，长窗口的 HSTS 会让站点在整个窗口内都进不去。这几步做的同时，`settings.py` 里的
`SILENCED_SYSTEM_CHECKS` 会自动放回对应的 `W008` / `W004` 告警——静音跟着开关走，不是写死的。

### 4.4 回滚

**回滚不能靠重跑 `deploy.sh`**：它第一步是备份（无害但会多留一份）、第五步却是**正向**
`migrate`，方向与回滚相反——用新代码的迁移去回滚旧代码只会把事情弄得更糟。

```bash
cd ~/applications/702platform
set -a; source env.sh; set +a
git checkout v1.0.0
.venv/bin/python manage.py migrate --noinput   # 仅当这一版带了迁移；反向迁移在旧 tag 的代码里
systemctl restart club702
```

> `env.sh` 与 `backups/` 都在 `.gitignore` 里，`git checkout` 不会动它们——回滚**不会**把配置和
> 备份一起退回去（这正是想要的：配置里有前一次发布补上的项，退回去反而可能过不了旧版门禁）。

**先反迁移、再切旧 tag**：若这一版**既有加列也有删表**（这条流水线上少见但要留意），顺序与平时
相反——先把删掉的表建回来、把加上的列去掉，再切旧 tag。反着做会让旧代码撞上「表没了」，站点起不来。

数据库也要退回时，用**发布前**那份备份手工恢复（它在 `RETAIN` 份内不会被提前清掉）：

```bash
systemctl stop club702
gunzip -c "$BACKUP_DIR/db-<发布前那份>.sql.gz" | PGPASSWORD="$DJANGO_DB_PASSWORD" \
    psql -U "$DJANGO_DB_USER" -h "${DJANGO_DB_HOST:-127.0.0.1}" "$DJANGO_DB_NAME"
systemctl start club702
```

恢复会覆盖当前数据，**确认过再执行**。

### 4.5 两条纪律

- **破坏性迁移**：删字段／删表／改类型**不要与依赖旧字段的功能同一次发布**——先加新列 +
  双写，下次发布再删旧列。保证任意一版代码与当版数据库兼容，回滚才安全。
- **搬过文件的迁移**（`core.0002_rehome_protected_uploads` 把受保护件从 `mediafiles/` 搬到
  `protected_media/`）**幂等**：两个根的相对路径相同，重跑只会发现目标已存在；数据库里指向的文件
  若已不在，只记一条 `private_media.missing` 警告并跳过，不中断整条迁移。反向迁移把文件搬回去。
- **删过模型的迁移之后**：跑一次 `.venv/bin/python manage.py remove_stale_contenttypes --noinput`，
  清掉 `django_content_type` 与 `auth_permission` 里指向已删模型的记录（`auth.Permission.content_type`
  是 CASCADE、`admin.LogEntry.content_type` 是 SET_NULL，所以这一步安全）。**它默认静默，没输出
  不等于没删**。不做的话，Admin 权限列表里会出现指向已不存在模型的条目。

### 4.6 配置的优先级与「生效值」

本项目**没有配置文件层，也没有命令行开关**——一切配置只有两个来源，后者覆盖前者：

1. **代码默认值**：`config/settings.py` 里 `os.environ.get("DJANGO_…", <默认>)` 的第二个参数。
2. **环境变量**：本地是 `env.local.sh`，生产是 `env.sh`（systemd 单元用 `EnvironmentFile` 读它）。

所以「改了代码默认值却不生效」几乎总是因为 **`env.sh` 里显式写着旧值**——它优先。改动安全开关
（Cookie、HSTS、SSL 跳转）时特别容易踩。看当前生效值（不打印密钥）：

```bash
set -a; source env.sh; set +a
.venv/bin/python -c "import os
for k in ('DJANGO_DEBUG','DJANGO_ALLOWED_HOSTS','DJANGO_SESSION_COOKIE_SECURE','DJANGO_CSRF_COOKIE_SECURE','DJANGO_PROXY_SSL_HEADER','DJANGO_SECURE_SSL_REDIRECT','DJANGO_SECURE_HSTS_SECONDS','DJANGO_CSRF_TRUSTED_ORIGINS','DJANGO_BACKUP_DIR','DJANGO_BACKUP_SCHEDULE'):
    print(f'{k}={os.environ.get(k, \"(未设，用代码默认值)\")}')"
```

## 5. 备份与恢复

备份由 `club702-backup.service`（oneshot）+ `club702-backup.timer` 驱动，不用 cron：统一由
systemd 管理、`systemctl list-timers` 可查、`Persistent=true` 可补跑错过的备份。

```bash
systemctl list-timers | grep club702
sudo -u club bash -c "cd /opt/702platform && source env.sh && ./deploy/backup.sh"   # 手动备份

# 恢复
gunzip -c backups/db-XXXX.sql.gz | PGPASSWORD=... psql -U club702 club702
tar -xzf backups/media-XXXX.tar.gz -C /opt/702platform
```

**媒体备份包含两个目录**：`mediafiles/`（公开配图）与 `protected_media/`（项目书、批注版、
头像、图册）。后者刻意不在前者之下，所以 `tar` 必须同时收两个；少一个会让受保护文件整批丢失，
而数据库里的路径还指着它们。`backup.sh` 与 `deploy.sh` 都已同时打包。保留份数由
`DJANGO_BACKUP_RETAIN` 控制（默认 14）。

**位置**：默认落在 `/var/backups/club702`（`DJANGO_BACKUP_DIR` 可改），**不在应用目录里**。
这一条防的是：systemd 给了应用进程整个应用目录的写权限，备份留在那里意味着**一旦 Web 应用被
攻陷，攻击者能删改备份**——而备份的意义正是「数据被改了还能回到从前」。**它防不住**拿到部署
用户 Shell 的人（属主就是它），所以三件事的优先级是：**异地副本 > 移出应用目录 > 加密**。
目录由 `install.sh`（有 sudo）一次性创建并 `chown`；`backup.sh` 每次运行会把权限收紧到
`700`（目录）与 `600`（文件）。

**加密**：`env.sh` 里填 `DJANGO_BACKUP_GPG_RECIPIENT` 即加密落盘，不填则明文保存并每次提醒。
备份里是实名身份、学号手机号与全部评审意见，比在线库更集中，值得加密。

**取回本地**：下载**时间戳相同**的一对文件——它们是分两步导出的，只取其一会出现「库里有记录、
文件没了」。取回后**在本地加密或放进加密盘**。

**一致性**：数据库与媒体分两步导出，不是同一时间点的快照，恢复后可能出现「库里有记录、媒体文件
缺失」。社团规模下这个窗口是秒级，可以接受；要严格一致就先停写。

**恢复演练（每季度一次，别只在出事时做）**——没验证过的备份不算备份。目标是在**另一处**把备份
变成能跑的服务，而不是「看着文件在」：① 取回一对时间戳相同的文件；② 在临时机器上用**相同的
`DJANGO_DB_*` 名字**建库；③ 恢复库与两个媒体目录，`manage.py migrate --check` 应当没有待应用的
迁移；④ 起 `runserver`，确认能登录、**受保护件能下载**、公开页的图能显示；⑤ 记下日期、备份
时间戳与结果（一行即可）——**这份记录本身就是审计证据**。

> 忘了 GPG 私钥等于没有备份，私钥要留在备份机而不是生产机上。

## 6. 运行时故障

### 6.1 日志与调试

**开发环境**日志同时输出到终端并写入 `logs/django.log`（`RotatingFileHandler`，单文件 10 MB、
保留 5 份、UTF-8）。**生产**用 `journalctl -u club702 -f` 看进程输出，应用内部日志仍是
`logs/django.log`。

每个请求生成 12 位 `request_id`，响应头 `X-Request-ID` 与日志一致，用于串联一次请求：

```text
request.start method=GET path=/ query= user=anonymous remote=127.0.0.1
request.end method=GET path=/ status=200 user=anonymous elapsed_ms=...
```

**排查顺序**：记下响应头 `X-Request-ID` → 在日志里搜这个 id → 看 `request.start` / `request.end`
的状态与耗时 → 如有 `request.exception` 读紧随的 traceback。按事件过滤：
`grep -E 'request\.start|request\.end|auth\.login|password_change|profile\.' logs/django.log`。

**安全**：不要把密码、完整 POST body 或 Cookie 写入日志；登录失败只记录用户名。

### 6.2 常见问题

| 现象 | 先查什么 |
|---|---|
| `No module named django` | 用了系统 Python——改用 `.venv/bin/python manage.py …` |
| `fe_sendauth: no password supplied` / 连接失败 | 忘了 `source env.sh`（或本地的 `env.local.sh`） |
| `no such table` | 未 `migrate`，或 `DJANGO_DB_NAME` / 账号有误 |
| 改了模型却提示有未生成的迁移 | `makemigrations` → `makemigrations --check --dry-run` → `migrate` |
| 登录后一直回到改密页 | 设计行为：确认新密码提交成功、库中 `must_change_password=False`、日志有 `password_change.success` |
| `DisallowedHost` | 把访问 IP／域名补进 `DJANGO_ALLOWED_HOSTS`（不带端口）后重启 |
| 端口被占用 | 换端口：`runserver 127.0.0.1:8765` |
| `DEBUG=0` 时页面无样式 | 忘记 `collectstatic`，或 Nginx 未映射 `/static/` |
| `DEBUG=0` 报 `Missing staticfiles manifest entry` | 生产启用了静态指纹，`collectstatic` 是硬要求 |
| `DEBUG=0` 时 `/media/` 404 | Nginx 未映射 `/media/` |
| 英文页面显示中文 | 缺 `gettext`（`sudo apt install gettext`），或部署时跳过了 `compilemessages` |
| 上传视频 413 | Nginx `client_max_body_size` 太小（模板已设 520m） |
| 看不到内部通知 | 成员未完成首次改密，或不属于通知绑定的用户组 |
| CSRF 验证失败（HTTPS 下） | 打开 `DJANGO_PROXY_SSL_HEADER` 与 `DJANGO_CSRF_TRUSTED_ORIGINS`（见 §4.3） |
| `check --deploy` 有安全警告 | 开发环境预期；生产完成 HTTPS 后配置环境变量再跑，**勿用 `SILENCED_SYSTEM_CHECKS` 掩盖** |

**已知限制**：审计日志的来源 IP 取自 `REMOTE_ADDR`，经 Nginx 代理后统一记为 `127.0.0.1`；
需要真实来源 IP 时须后续增加可信代理配置（见 [`模块与关系.md`](模块与关系.md) §5）。

### 6.3 审计日志：改不动是数据库在守，以及它的逃生口

审计表上挂着行级触发器 `core_auditlog_append_only`：任何 `UPDATE` / `DELETE` 命中即
`RAISE EXCEPTION`。这是**有意挡住正常路径的**——数据修复脚本、`queryset.update()`、数据库
客户端都改不动留痕里的某一行，**别看到报错就去把触发器摘掉**。

两个真实的副作用，先知道再遇到：

- **有审计行的账号删不掉**：`AuditLog.user` 是 `SET_NULL`，删用户前要先把他名下的审计行置空
  （一次 `UPDATE`）——而那被触发器挡住。在后台点删除的**页面结果是 500**。账号退场的正常口径是
  **停用**（后台取消 `is_active`），不是删除。
- **归档审计日志**（按年份清理旧行）也不能直接 `DELETE`，得走逃生口。

**逃生口**（两条，都不改代码、不改迁移）：

```sql
-- 甲之一：临时摘掉触发器（要表属主，即应用账号；只影响这一张表）
ALTER TABLE core_auditlog DISABLE TRIGGER core_auditlog_append_only;
--   ……做完清理/归档，立刻装回去；装回去之前这张表没有任何保护：
ALTER TABLE core_auditlog ENABLE TRIGGER core_auditlog_append_only;

-- 乙：superuser 会话里关掉本会话的触发器执行（不动表定义，作用域限于这个连接）
SET session_replication_role = replica;   -- 同一个连接里做完，退出即失效
```

甲的两条**别整块复制**（那样等于摘下来又立刻装上，中间什么都没做）；它要给表加
`ACCESS EXCLUSIVE` 锁，站点在用的话会短暂阻塞对审计表的读写，挑低峰做。**做完读回确认**：
`\d core_auditlog` 里 `Triggers` 一栏应重新出现该触发器。

> 触发器抛出的那句 `RAISE EXCEPTION` 文案写在**已应用的迁移** `core.0003` 里，里面
> 指的是旧路径 `docs/deploy.md §5.3`。线上库里的触发器是那次迁移建出来的，改文件不会
> 改到它，加一条迁移只为改一句提示又不值当——**照着本节找就是**。

**能挡住什么**：行级 `UPDATE` / `DELETE`（含 ORM 与脚本）。**挡不住**：整表级与 DDL 级动作
（`TRUNCATE`——`manage.py flush` 走的就是它、`DROP TABLE`、从备份整库恢复、`ALTER TABLE`），
以及上面两条逃生口。也就是说留痕不会被某段代码或某个人悄悄改掉一行，但「把库整个换掉」这种
级别的操作，任何应用层护栏都拦不住，靠的是备份与权限。

### 7.1 容量与扩展

单台服务器、单进程 gunicorn、数据库在本机——社团规模下够用，但有几处会先满：

| 会先满的 | 满了怎么办 |
|---|---|
| **磁盘** | 先看 `du -sh mediafiles protected_media logs`；媒体是增长主项，可把 `DJANGO_BACKUP_RETAIN` 调小或把备份挪到更大的盘 |
| **上传体积** | 改 Nginx 模板要「先 `deploy.sh` 再 `install.sh`」，并读回 `/etc` 下的文件核对 |
| **并发** | 加 gunicorn worker 数（`club702.service` 的 `--workers`）；真到瓶颈先量再改 |
| **数据库** | 审计日志可按年份归档，但**清理要先走 §6.3 的逃生口**；消息表有按来源的级联清理 |
| **媒体文件数** | 公开件按 `uploads/%Y/%m/` 分目录，受保护件按类型 + `%Y/%m/` 分；单目录几十万文件才需再分片 |

### 7.2 废弃与退役

- **旧版本**：服务器上的代码**只从 git tag 取**（`deploy.sh` 强制），任意历史 tag 都能
  `git checkout` 回去；数据库侧靠「破坏性迁移纪律」保证任一版代码与当版库兼容。
- **证书与域名**：换证书只改 `env.sh` 的两个路径 + `install.sh` 重渲染续期单元；**退役某个入口**
  （域名或 IP）要从 Nginx 模板的 `server_name` 与 `DJANGO_CSRF_TRUSTED_ORIGINS` 里同时去掉，
  否则表单提交会因 Origin 校验失败。
- **整站下线顺序**：① 公告通知成员 → ② 停 `club702.service` → ③ 最后备份一次库与**两个**媒体
  目录 → ④ 把备份取回本地并确认可读 → ⑤ 再决定何时删除服务器上的数据与续期单元。
- **成员数据**：备份里有实名身份、学号手机号与全部评审意见。退役时按所在组织的留存要求处理
  ——**先备份、后删除，且别把备份留在即将释放的机器上**。

## 8. 新增一个功能：拿一个真实功能走一遍

以「项目组列表：搜索 + 我的项目组」（`projects`）为例，从口径到提交的完整落点。它把
「跨表查询、可见性收窄、GET 表单、测试怎么挑」都碰了一遍——照着走一遍，就知道新功能该落在
哪几个文件里。

**1. 先定口径，再写代码。** 这个功能有三条口径必须在动手前问清楚：

- 搜索能越过可见性吗？——不能。`groups_visible_to` 给定的范围是**前提**，搜索是在它之内收窄。
- 「我的项目组」包含哪些？——`member_group_ids`：联系人一定在成员名单里（`ProjectGroup.save` 保证），
  所以成员那一侧就是「联系人 ∪ 组员」。
- 关键字认哪些名字？——组名 + 联系人／成员／指导老师三种姓名；姓名同时认 `Profile.full_name` 与
  `username`（后者是 `full_name` 为空时页面回退显示的名字）。

问答都落进 [`模块与关系.md`](模块与关系.md) 与 [`../术语表.md`](../术语表.md)；新概念先在术语表里定名。

**2. 改哪几个文件**（顺序就是依赖方向）：`selectors.py` 加收窄查询（跨一对多关系过滤，结尾
`distinct()`）→ `permissions.py` 收「我参与的组」→ `views.py` 组装 → 模板 → 测试。

**3. 数人不能用 `Count("members")`**：`search_groups` 已经 JOIN 了 `members`，聚合落在那条
**被过滤过的** join 上时，过滤会把参与聚合的行一起筛掉——搜「高」（只命中 1 名成员）时卡片写
「成员 1 人」，而下面列着 5 个人。用子查询数与过滤各走一条 join。

**4. 测试要挑有判别力的**：写用例时问一句：**改坏哪一行会让它变红？**答不上来的是装饰，不是测试。
这一段里有个现成的例子：钉住 `distinct()` 的那条用例曾经没有判别力（外层恰好有个 `GROUP BY`
顺手把重复行收成了一行，断言其实落在别人的副作用上），改成子查询数人之后才真正钉住它。
**答案会随后续改动变化，别一直信旧答案。**
