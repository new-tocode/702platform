## 1. 环境

数据库**固定 PostgreSQL**（Django 5.2 要求 ≥14），连接参数写在根目录 `env.local.sh`；
怎么把项目跑起来见 [`../../README.md`](../../README.md) 的「快速开始」。

**SQLite 已移除**——看到 `fe_sendauth: no password supplied` 之类错误即是忘了 source。
生产要装的系统包、首次部署的命令、`env.sh` 该填什么，见 §4.1 与 [`deploy/install.sh`](../../deploy/install.sh)。

**依赖用锁文件 + `--require-hashes`**：每个包按哈希校验，依赖被篡改或供应链投毒会当场失败。
`--generate-hashes` 会把**所有平台**的轮子哈希都收进锁文件，所以本地 3.13 生成的锁文件在生产
3.12 上一样能装。验证方式（不下载，只按目标平台解析）：

```bash
pip download --require-hashes -d /tmp/chk \
  --python-version 312 --implementation cp --abi cp312 \
  --platform manylinux_2_17_x86_64 --only-binary :all: -r requirements.txt
```

**升级依赖后要留意两件事**：① **glibc 版本**——Pillow 12.x 的 Linux 轮子改用 `manylinux_2_28`
标签（要求 glibc ≥ 2.28），换更老的系统会退回源码编译；② **跑一遍全量测试**，尤其图片解压炸弹
那几条（防护依赖 Pillow 的 `DecompressionBombError` 与 `MAX_IMAGE_PIXELS`，**主版本升级必须确认
这两个还在、行为没变**）。

**一个数据库扩展**：`content.0004_pg_trgm` 会 `CREATE EXTENSION pg_trgm`。它是 **contrib 扩展、
不随 server 包一起装**，只装 server 的机器上第一次 migrate 就会失败——装哪个包、报错长什么样、
为什么不需要重启 PostgreSQL，都写在**那条迁移的 docstring** 里；部署脚本在 migrate 前会先探一次。

## 3. 注释怎么写

代码里的注释是**中文自由式**，只服务一条原则：**写代码看不出来的东西**——为什么这么做、
边界在哪、什么时候会失败。签名里读得出来的（参数名、返回什么）不写；「先取对象、再校验」
这种把代码念一遍的也不写。

| 位置 | 写什么 |
|---|---|
| 模块 docstring | 这个模块负责什么、**为什么把它单独拆出来** |
| 公开函数 | 语义、前置条件、**失败模式**：抛哪个领域异常、视图会把它翻译成什么；拒绝时是 403 还是 404 |
| 行内注释 | 只有一种：**为什么非得这么写**。反直觉的写法、必须维持的顺序、看起来多余却不能删的那一行 |

**失败模式是当前最缺的一条。**读代码时最费劲的不是「它做了什么」，而是「什么情况下它会
拒绝我、以什么形式拒绝」。服务层抛领域异常、视图翻成 `messages` 或 403/404——新写服务函数时
把这条写进 docstring。

几条具体的：**并发与锁要写明**（靠行锁保证正确性时，docstring 里写清锁的是哪一行、为什么非锁
不可——这是最容易在重构时被当作冗余删掉的一行）；**不写会过期的数字**（条数、行数、耗时写在
提交信息里）；**交叉引用用 Sphinx 式**（`:func:` / `:class:`，与既有代码一致；项目不接文档
生成器，它只是给人跳转用）；**不复述模型字段**（字段含义写在 `models.py` 的定义处）。

## 4. 部署

### 4.1 形态与安装

**部署形态**：单台服务器、gunicorn（systemd）+ Nginx 反代与静态服务、PostgreSQL 在本机。
**不支持**多机／对象存储／灰度发布——要换形态时媒体层是留好的接缝（见 [`../../media/README.md`](../../media/README.md)）。
数据在 PostgreSQL，受保护上传件在应用目录下的 `protected_media/`，配置在 `env.sh`（**不入库**）。

首次部署跑 `deploy/install.sh`：它**检测到依赖或配置不符合就中止，绝不自动下载安装任何软件**；
`env.template` 里的 `<尖括号>` 占位符是硬门禁，不会放行「复制模板后忘了替换」。脚本自身带
职责清单与逐项校验提示，照它做即可。

### 4.2 更新

`deploy/deploy.sh <tag>` 一条命令，它内部的步骤编号与失败即中止的行为都在脚本里（含
`0/6` 上线前预检：证书与备份）。两件从代码里看不出来的：

- **配置门禁会拦下**「`DEBUG` 还开着」「Cookie 没带 Secure」「`SECRET_KEY` 还是源码默认值」这类
  **不会让站点起不来、只会让它安静地不安全**的问题——宁可发布失败。
- **健康检查要看清验到了哪一层**：通过后它会打印 `经 Nginx（…）` 还是 `直连 gunicorn（…）`。
  **两种结果含义不同**——成员走的是 Nginx 那条路，只验到直连等于**没验到成员看到的那一层**；
  看到「直连」就去查 Nginx，别当成绿灯。

### 4.3 HTTPS

证书走 Let's Encrypt 的 **IP 地址证书**（不需要域名、也不需要备案），由独立 venv 里的
certbot 签发与续期；`install.sh` 发现还没签证书时会把签发命令打出来。证书是
**shortlived profile，只有几天有效期**（不是 90 天），所以续期 timer 一天跑两次是硬需求：
certbot 在剩余不足寿命 1/3 时才动手续，一天两次意味着到期前有若干次尝试机会。

**这台机器上可能有两个 certbot，手动碰证书时最容易踩这个坑。**发行版仓库那个
（`/usr/bin/certbot`）认不出 IP 证书，`renew` 会报
`At least one of domains or ipaddrs parameter need to be not empty`——**这是假故障**，
真正负责续期的那个（`env.sh` 的 `CERTBOT_BIN`，要求 ≥ 5.4）一切正常。分辨方法：输出里
`Simulating renewal of an existing certificate for` 后面**空着**就是跑错了二进制。所以这类
命令一律写全路径。**另有两条容易误读的输出**：到 `acme-staging-v02.api.letsencrypt.org` 的
`ReadTimeout` 是网络抖动（`--dry-run` 走 staging），重试即可；`certbot reconfigure` 说
`No changes were made to the renewal configuration.` 不是失败——它是在 staging 试续**成功之后**
才说这句，意思是「配置已经就是这样」。


**四个开关要一起设**（`env.sh` 里显式写死的值会**覆盖**代码默认值，所以升级时必须改文件）：

```bash
DJANGO_SESSION_COOKIE_SECURE=1     # Cookie 上的 Secure 属性由它直接决定
DJANGO_CSRF_COOKIE_SECURE=1
DJANGO_PROXY_SSL_HEADER=1          # 让 Django 知道请求其实是 https
DJANGO_CSRF_TRUSTED_ORIGINS=https://<域名>,https://<公网IP>   # 成员实际访问的每个入口都要写
```

前三项改完才能通过 `check --deploy` 门禁（否则以 `security.W012` / `W016` 中止部署——有意
设计：宁可发布失败，也不让站点安静地不安全）。`DJANGO_SECURE_SSL_REDIRECT` 与
`DJANGO_SECURE_HSTS_SECONDS` **继续留空或 0**。

**第四项不是可选项，漏填的后果是表单提交 403。**Django 每次 POST 都会把浏览器发来的
`Origin` 头与「`request.is_secure()` 判断出的协议 + Host」比对，对不上就拒绝。生产上 TLS 由
Nginx 终结、Django 自己看不出是 https（除非开 `PROXY_SSL_HEADER`），于是它期望 `http://…`
而浏览器发的是 `https://…`，必然对不上。**注意这一项不在 `check --deploy` 的检查项里**：
门禁拦不下它，症状要等成员提交表单时才出现，所以照着模板逐字确认，别凭印象。

`SESSION_COOKIE_SECURE` 与 `PROXY_SSL_HEADER` 是两件事，别搞混：前者**直接决定** Cookie 带不带
`Secure`；后者管的是让 Django 知道「这个请求其实是 https」，影响 `request.is_secure()`、
CSRF 的 Origin 校验、以及 `SECURE_SSL_REDIRECT` 会不会误判成死循环。

**四个开关的实测组合**（入口走 https、Nginx 发 `X-Forwarded-Proto: https`）：

| 配置 | `is_secure()` | Origin 校验 |
|---|---|---|
| 两项都不设 | False | **拒绝** |
| 只改 `PROXY_SSL_HEADER=1` | True | 通过，但会**追加** Referer 校验（Django 对 HTTPS 的额外保护） |
| 只加 `TRUSTED_ORIGINS` | False | **仍拒绝**（`is_secure()` 没变） |
| **两个都设** | True | **通过** ← 正确组合 |

**为什么以前「看起来能用」**：**不带 `Origin` 头**的 POST 在 `is_secure()=False` 时不做校验，
就侥幸过了；带 `Origin` 头的现代浏览器请求会被拒。所以这是「**偶发**提交失败」的来源，
不是一直坏——排查时别因为「昨天还好好的」就排除这一项。

**顺序**：① 先换证书本身、确认 HTTPS 正常 → ② 设受信来源 → ③ 确认没有 http 访问需求后再开
整站跳转（`DJANGO_SECURE_SSL_REDIRECT=1`）→ ④ HSTS **最后**再考虑。

**开整站跳转前先确认 `server_name`**：IP 证书覆盖不了域名，站点若还留着一个域名入口，
硬跳会把它跳到一张**不匹配的证书**上（浏览器直接拦下，比不跳更糟）。

HSTS 那一步：先给一个很短的窗口
（`DJANGO_SECURE_HSTS_SECONDS=60`）试水。**加长到一年之前想清楚证书续期是不是自动的**——
证书一断，长窗口的 HSTS 会让站点在整个窗口内都进不去。这几步做的同时，`settings.py` 里的
`SILENCED_SYSTEM_CHECKS` 会自动放回对应的 `W008` / `W004` 告警——静音跟着开关走，不是写死的。

### 4.4 回滚

**回滚不能靠重跑 `deploy.sh`**：它第一步是备份（无害但会多留一份）、第五步却是**正向**
`migrate`，方向与回滚相反——用新代码的迁移去回滚旧代码只会把事情弄得更糟。

```bash
cd ~/applications/702platform
set -a; source env.sh; set +a
git checkout v1.0.0
.venv/bin/python manage.py migrate --noinput   # 仅当这一版带了迁移；反向迁移在旧 tag 的代码里
systemctl restart club702
```

> `env.sh` 与 `backups/` 都在 `.gitignore` 里，`git checkout` 不会动它们——回滚**不会**把配置和
> 备份一起退回去（这正是想要的：配置里有前一次发布补上的项，退回去反而可能过不了旧版门禁）。

**先反迁移、再切旧 tag**：若这一版**既有加列也有删表**（这条流水线上少见但要留意），顺序与平时
相反——先把删掉的表建回来、把加上的列去掉，再切旧 tag。反着做会让旧代码撞上「表没了」，站点起不来。

数据库也要退回时，用**发布前**那份备份手工恢复（它在 `RETAIN` 份内不会被提前清掉）：

```bash
systemctl stop club702
gunzip -c "$BACKUP_DIR/db-<发布前那份>.sql.gz" | PGPASSWORD="$DJANGO_DB_PASSWORD" \
    psql -U "$DJANGO_DB_USER" -h "${DJANGO_DB_HOST:-127.0.0.1}" "$DJANGO_DB_NAME"
systemctl start club702
```

恢复会覆盖当前数据，**确认过再执行**。

### 4.5 两条纪律

- **破坏性迁移**：删字段／删表／改类型**不要与依赖旧字段的功能同一次发布**——先加新列 +
  双写，下次发布再删旧列。保证任意一版代码与当版数据库兼容，回滚才安全。
- **回填型迁移的取向：认不出的历史数据留空，不否决。**获奖记录认不出层级就留空（空层级不参与
  判重），老轮次没有送审类型就回退到默认人数；指向的文件已不在盘上时只记一条
  `private_media.missing` 警告并跳过，**不中断整条迁移**。宁可让个别历史行带着空值，也不要让
  一次发布卡在半路。
- **搬过文件的迁移**（`core.0002_rehome_protected_uploads` 把受保护件从 `mediafiles/` 搬到
  `protected_media/`）**幂等**：两个根的相对路径相同，重跑只会发现目标已存在；数据库里指向的文件
  若已不在，只记一条 `private_media.missing` 警告并跳过，不中断整条迁移。反向迁移把文件搬回去。
- **删过模型的迁移之后**：跑一次 `.venv/bin/python manage.py remove_stale_contenttypes --noinput`，
  清掉 `django_content_type` 与 `auth_permission` 里指向已删模型的记录（`auth.Permission.content_type`
  是 CASCADE、`admin.LogEntry.content_type` 是 SET_NULL，所以这一步安全）。**它默认静默，没输出
  不等于没删**。不做的话，Admin 权限列表里会出现指向已不存在模型的条目。

### 4.6 配置的优先级与「生效值」

本项目**没有配置文件层，也没有命令行开关**——一切配置只有两个来源，后者覆盖前者：

1. **代码默认值**：`config/settings.py` 里 `os.environ.get("DJANGO_…", <默认>)` 的第二个参数。
2. **环境变量**：本地是 `env.local.sh`，生产是 `env.sh`（systemd 单元用 `EnvironmentFile` 读它）。

所以「改了代码默认值却不生效」几乎总是因为 **`env.sh` 里显式写着旧值**——它优先。改动安全开关
（Cookie、HSTS、SSL 跳转）时特别容易踩。看当前生效值（不打印密钥）：

```bash
set -a; source env.sh; set +a
.venv/bin/python -c "import os
for k in ('DJANGO_DEBUG','DJANGO_ALLOWED_HOSTS','DJANGO_SESSION_COOKIE_SECURE','DJANGO_CSRF_COOKIE_SECURE','DJANGO_PROXY_SSL_HEADER','DJANGO_SECURE_SSL_REDIRECT','DJANGO_SECURE_HSTS_SECONDS','DJANGO_CSRF_TRUSTED_ORIGINS','DJANGO_BACKUP_DIR','DJANGO_BACKUP_SCHEDULE'):
    print(f'{k}={os.environ.get(k, \"(未设，用代码默认值)\")}')"
```

## 5. 备份与恢复

备份由 `club702-backup.{service,timer}` 驱动（不是 cron），命令与用法见 [`deploy/backup.sh`](../../deploy/backup.sh)。
这一节只记**从代码里读不出来**的几条：

- **媒体备份必须同时收两个目录**：`mediafiles/`（公开配图）与 `protected_media/`（项目书、批注版、
  头像、图册）。后者刻意不在前者之下，所以 `tar` 少收一个会让受保护文件**整批丢失**，而数据库里的
  路径还指着它们。`backup.sh` 与 `deploy.sh` 都已同时打包；自定义脚本时留意。
- **`backup.sh` 自己的兜底值在「应用目录内」，与推荐的 `/var/backups/...` 不同——这是有意的。**
  它由 systemd 每天自动跑，兜底值指向一个尚未创建的外置目录会让**备份直接失败**（比备份在应用目录
  内更糟）。新部署由 `install.sh` 建目录、`env.template` 写路径；**读到脚本里那个默认值时别当成写错了**。
- **备份位置为什么必须在应用目录之外**：systemd 给了应用进程整个应用目录的写权限，备份留在那里
  意味着**一旦 Web 应用被攻陷，攻击者能删改备份**——而备份的意义正是「数据被改了还能回到从前」。
  **它防不住**拿到部署用户 Shell 的人，所以优先级是：**异地副本 > 移出应用目录 > 加密**。

**取回与演练的纪律**（这几条代码里没有）：

- 取回本地时下载**时间戳相同**的一对文件——库与媒体是分两步导出的，只取其一会出现「库里有记录、
  文件没了」。取回后**在本地加密或放进加密盘**：备份里有实名身份、学号手机号与全部评审意见。
- **忘了 GPG 私钥等于没有备份**，私钥要留在备份机而不是生产机上。
- 库与媒体不是同一时间点的快照，恢复后可能出现「库里有记录、媒体文件缺失」；社团规模下这个窗口是
  秒级，要严格一致就先停写。
- **每季度做一次恢复演练**，目标是在**另一处**把备份变成能跑的服务，而不是「看着文件在」：恢复库与
  两个媒体目录 → `migrate --check` 应无待应用迁移 → 起服务确认能登录、**受保护件能下载**、公开页的图
  能显示。记下日期与结果（一行即可）——**这份记录本身就是审计证据**。

## 6. 审计日志：改不动是数据库在守，以及它的逃生口

审计表上挂着行级触发器 `core_auditlog_append_only`：任何 `UPDATE` / `DELETE` 命中即
`RAISE EXCEPTION`。这是**有意挡住正常路径的**——数据修复脚本、`queryset.update()`、数据库
客户端都改不动留痕里的某一行，**别看到报错就去把触发器摘掉**。

两个真实的副作用，先知道再遇到：

- **有审计行的账号删不掉**：`AuditLog.user` 是 `SET_NULL`，删用户前要先把他名下的审计行置空
  （一次 `UPDATE`）——而那被触发器挡住。在后台点删除的**页面结果是 500**。账号退场的正常口径是
  **停用**（后台取消 `is_active`），不是删除。
- **归档审计日志**（按年份清理旧行）也不能直接 `DELETE`，得走逃生口。

**逃生口**（两条，都不改代码、不改迁移）：

```sql
-- 甲之一：临时摘掉触发器（要表属主，即应用账号；只影响这一张表）
ALTER TABLE core_auditlog DISABLE TRIGGER core_auditlog_append_only;
--   ……做完清理/归档，立刻装回去；装回去之前这张表没有任何保护：
ALTER TABLE core_auditlog ENABLE TRIGGER core_auditlog_append_only;

-- 乙：superuser 会话里关掉本会话的触发器执行（不动表定义，作用域限于这个连接）
SET session_replication_role = replica;   -- 同一个连接里做完，退出即失效
```

甲的两条**别整块复制**（那样等于摘下来又立刻装上，中间什么都没做）；它要给表加
`ACCESS EXCLUSIVE` 锁，站点在用的话会短暂阻塞对审计表的读写，挑低峰做。**做完读回确认**：
`\d core_auditlog` 里 `Triggers` 一栏应重新出现该触发器。

> 触发器抛出的那句 `RAISE EXCEPTION` 文案写在迁移 `core.0003` 里。**已跑过这条迁移的库不会再跑
> 一遍**，所以那些库的报错文案还是旧路径；新装的机器会照当前文件生成，拿到的是新路径。为一句提示
> 加一条迁移不值当——**照着本节找就是**。

**能挡住什么**：行级 `UPDATE` / `DELETE`（含 ORM 与脚本）。**挡不住**：整表级与 DDL 级动作
（`TRUNCATE`——`manage.py flush` 走的就是它、`DROP TABLE`、从备份整库恢复、`ALTER TABLE`），
以及上面两条逃生口。也就是说留痕不会被某段代码或某个人悄悄改掉一行，但「把库整个换掉」这种
级别的操作，任何应用层护栏都拦不住，靠的是备份与权限。

## 7. 退役

- **旧版本**：服务器上的代码**只从 git tag 取**（`deploy.sh` 强制），任意历史 tag 都能
  `git checkout` 回去；数据库侧靠「破坏性迁移纪律」保证任一版代码与当版库兼容。
- **证书与域名**：换证书只改 `env.sh` 的两个路径 + `install.sh` 重渲染续期单元；**退役某个入口**
  （域名或 IP）要从 Nginx 模板的 `server_name` 与 `DJANGO_CSRF_TRUSTED_ORIGINS` 里同时去掉，
  否则表单提交会因 Origin 校验失败。
- **整站下线顺序**：① 公告通知成员 → ② 停 `club702.service` → ③ 最后备份一次库与**两个**媒体
  目录 → ④ 把备份取回本地并确认可读 → ⑤ 再决定何时删除服务器上的数据与续期单元。
- **成员数据**：备份里有实名身份、学号手机号与全部评审意见。退役时按所在组织的留存要求处理
  ——**先备份、后删除，且别把备份留在即将释放的机器上**。

## 8. 新增一个功能：拿一个真实功能走一遍

以「项目组列表：搜索 + 我的项目组」（`projects`）为例，从口径到提交的完整落点。它把
「跨表查询、可见性收窄、GET 表单、测试怎么挑」都碰了一遍——照着走一遍，就知道新功能该落在
哪几个文件里。

**1. 先定口径，再写代码。** 这个功能有三条口径必须在动手前问清楚：

- 搜索能越过可见性吗？——不能。`groups_visible_to` 给定的范围是**前提**，搜索是在它之内收窄。
- 「我的项目组」包含哪些？——`member_group_ids`：联系人一定在成员名单里（`ProjectGroup.save` 保证），
  所以成员那一侧就是「联系人 ∪ 组员」。
- 关键字认哪些名字？——组名 + 联系人／成员／指导老师三种姓名；姓名同时认 `Profile.full_name` 与
  `username`（后者是 `full_name` 为空时页面回退显示的名字）。

问答都落进 [`模块与关系.md`](模块与关系.md) 与 [`../术语表.md`](../术语表.md)；新概念先在术语表里定名。

**2. 测试要挑有判别力的**：写用例时问一句：**改坏哪一行会让它变红？**答不上来的是装饰，不是测试。
每一条断言都该能说出它钉住的是哪一行——**而且答案会随后续改动变化，别一直信旧答案**：断言可能
因为外层恰好多了一个 `GROUP BY`、多了一次 `distinct()` 而落在别人的副作用上，看着是绿的，其实
什么都没钉住。改用例时把这个问题重问一遍。

**3. 文档跟着改**：口径变了改 [`模块与关系.md`](模块与关系.md) 或对应模块的 README；新文案进模板后
要跑 i18n 那一套（见 [`../../CLAUDE.md`](../../CLAUDE.md) §4）；若新增了成员入口，去 `core.registry` 登记。

**4. 提交**：`compileall` → `check` → `makemigrations --check --dry-run` → `test` 全过再提交，
提交信息讲清**为什么这么改**并附测试结果。跨多个模块的改造先切分支、写一份可勾选的 `TASKS.md`
（被 `.gitignore` 忽略，做完删掉），每个阶段一个提交。
