# notices 模块

> 站内通知与消息：管理员发布的**公告**（`Notice`，三种可见范围）、成员侧的「我的消息」页、
> **事件型消息**（`Message`，一行一个收件人），以及其中唯一一种由成员自己发起的**私信**
> （`DirectMessage`，正文单独一张表）。公告由后台发布，别的事件的消息由别的 app 在自己的事务里调
> `services.py` 写入。
> **它不判「谁能做什么」**（本 app 没有 `permissions.py`），不解析 @ 提及（归 `discussion.mentions`），
> 不渲染**别的 app** 的消息点开后那一页（帖子／项目组／评审队列各归其主；私信没有别的主人，
> 它的详情页归本模块），也不替别的 app 写事务与审计。

**什么时候看**：加一种消息 kind、改可见范围口径、改「我的消息」的列与未读计数、动已读回执、
改公告的后台表单、碰私信（正文上限、读完的处置、浮动窗），
或者排查「这条消息为什么看不见／为什么没消掉」时。

---

## 1. 明确不做什么

| 不在这里 | 落在哪 |
|---|---|
| 权限判定 | **本 app 没有 `permissions.py`，也不 import `core.permissions`**：成员页只有 `@login_required`，越权表现为「取不到对象」→ 404，不是 403 |
| @ 提及「提了谁」的解析 | `discussion.mentions.extract_mentions`；本模块只按解析结果对齐消息行 |
| 别的 app 的消息点开后的目标页 | 帖子、项目组、建组申请各归其主；`message_go` 只标已读 + 302。私信不在此列——它的详情页就是本模块的 `direct_detail` |
| 任务的生命周期与历史 | `reviews`：消息只负责「有事等你」，交掉／释放／改派后待办被撤掉，历史留在评审页 |
| 配图／视频的存储与可见性 | `media.MediaFile`：媒体库是**公开件**（落 `mediafiles/`、Nginx 直出、匿名可访问），公告附件没有权限判定 |
| 强制改密的拦截 | `config.middleware.ForcePasswordChangeMiddleware`；本模块只是被它拦住的页面之一 |
| 事务边界（**分两种，别按「一律」记**） | 别的 app 发起的消息写在**调用方**（`projects` / `reviews` / `discussion`）的事务里，本模块不开事务；已读是单条幂等写；**私信是本模块自己发起的写**，正文与通知两行必须一起落，所以那一处自己开事务。本模块不 `select_for_update` |
| 私信的**写** | 成员侧的三个视图是唯一的写入口；后台只有一只只读的表（无增改删），不写审计。出了争议，后台看得到「谁给谁发过什么」，但那是一条**可删**的记录——不是底账 |
| 已读的审计 | 刻意不写（已读是高频、个人、幂等的操作）。全模块只有后台发布公告写 `notices.create` / `notices.update` |

## 2. 必须成立的断言

- **可见性是查询集，不是权限位**：`member_visible_notices(user)` 是成员侧可见集合的唯一出处，
  列表、详情、未读计数、「全部已读」、置顶排序前的取数全走它；加一条 scope 只改这里。
  它由三段并集构成，最后 `distinct()` 收掉「一条通知命中我两个组」的重复行。
- **不物化消息副本**：广播型没有「某人有一条通知行」，未读 = 可见通知 − 回执；事件型一行一个收件人、
  没有可见集合可言。所以删除来源后成员侧自然消失。
- **事件消息的可显示字段（标题／链接／来自／说明）一律现取现算**：帖子改了标题、轮次出了新结论、
  申请通过了，消息里跟着变；行里只有结构化引用与已读状态。私信的正文同样取自 `DirectMessage`
  ——「正文没有第二个家」与「消息行不存副本」是同一条性质的两种说法。
- **`kind` 要同时出现在三处**：`Message.KIND_CHOICES`、`selectors._CONTENT_BUILDERS`、
  `selectors._TYPE_LABELS`。漏了第二处该行被静默跳过（记 warning），漏了第三处装配时直接
  `KeyError`（整页 500）；`MessageKindCoverageTests` 钉着这三处的集合相等。
- **私信的两行同生同死**：`send_direct_message` 在一个事务里写正文与通知；删除走
  `delete_direct_message` 删正文、通知行跟着 `CASCADE`。所以「我的消息」里出现过的私信行，
  背后必有一条正文（**除非**绕过写入函数直接建行——那种行在取数时就被排除）。
- **能不能回给发信人只有一个判定**：`selectors.direct_reply_target`——发信人**在册**才有得回，
  注销与**停用**都不给「快速回信」／「回复」。这与写私信那道门（收信人 `is_active=True`）是同一个条件，
  两边一致按钮才不会点出 404；**停用是本平台真正的账号退场口径**，所以这条判定不能只看
  「外键是不是 NULL」。
- **私信读完不消失**：已读只动 `is_read` / `read_at`。要它走只有一条路——收信人在 `direct_detail`
  上按「删除私信」。这与「来源删除即级联删行」并不冲突：那一头是**别的 app 删了自己的东西**。
- **一条私信只给收信人一行**：发信人自己的「我的消息」里不会有它；也没有「已发送」这类列表。
- **进入详情即已读**：`internal_detail` 的 GET 写回执，公开公告栏那条路不写——同一条公开通知，
  在公告栏看多少次都不会消掉「我的消息」里的未读角标。
- **已读与撤回是两条路**：撤回（三个 `clear_*`）直接 `delete()`，不看已读状态；
  重对齐（`sync_mention_messages`）只增删行，**不把留下的人重新标成未读**。
- **一条评论最多给帖主一条消息**：他自己评论自己的帖子不发；别人在评论里 @ 到了他，也只留那条提及。
  为此 `discussion` 那边必须**先写提及、再调 `notify_comment`**——顺序反了就会同一条评论并列两条。
- **后台表单是「范围 × 用户组」搭配的唯一执行点**：`internal` 必须至少一个用户组，`public` / `contacts`
  不许带用户组。`Notice` 没有模型级 `clean()`，`save()` 也不跑 `full_clean()`——绕过 admin 能造出
  永远不可见的 internal 通知，或带着用户组但照常对所有人可见的 public 通知。

## 3. 已知限制 / 当前不支持

- **本模块没有任何权限判定**（没有 `permissions.py`，也不 import `core.permissions`）：成员页门槛只有
  `@login_required`。以后要加「只有谁能做什么」的页面动作，判定应落 `core.permissions` 或新建
  `permissions.py`，别写在视图里——否则可见性就有了第二处真相。
- **「internal 必须有用户组」只在后台表单把关**：数据库与模型都没有这条约束。绕过 admin 建出的
  internal 通知对所有成员都不可见；带用户组的 public / contacts 通知照常对所有人可见（用户组被忽略）。
- **公告附件没有可见性判定**：`attachments` 指向公开媒体库，URL 由 Nginx 直出。内部通知的正文受可见集合
  保护，配图不在这道保护里——往内部／联系人通知挂配图时要知道这一点。
- **`notify_create_request` 的收件人是申请那一刻的管理员快照**，且没有 `is_active` 过滤（被停用的管理员
  仍在收件人里）。这份内联口径与 `core.permissions.is_admin` 目前一致，但**改后者不会自动改这里**。
- **`internal_detail` 是 GET 写库**：没有 `require_GET` / `require_POST`，POST 同样会写回执。
  回执幂等、写的是本人的行，风险可控，但「这个 URL 是只读的」不成立。
- **「我的消息」不分页**：`message_rows` 一次装配全部行，每装配一条提及还要查一次它所在帖子的页码
  （`page_of_post` 会把该板块的帖子 id 全捞进内存）。提及多的账号打开这一页要按行数付查询。
- **编辑帖子会真的删掉提及消息**：不再被提到的人直接 `delete()`，已读的也删——「我的消息」里不会留下
  「这条提及已撤销」的痕迹。这是刻意的对齐语义，但改它要连带考虑已读与计数的一致。
- **私信没有「已发送」列表**：发信人看不到自己发出去的私信；删掉收信人那一行也就再没有别处留着它。
  这是本轮刻意的边界——需求里只要求收信人能读、能删、能回。
- **私信正文的上限只在表单把关**：模型字段的 `max_length` 与数据库都没有拦（PostgreSQL 的 `text` 不限长），
  绕过 `DirectMessageForm` 直接调 `services.send_direct_message` 能存进超长正文。
- **没有「不能给自己发」的库约束**：服务层与视图各挡一次，`DirectMessage` 上没有 `CheckConstraint`。
- **「快速回信」本身不标已读**：它只打开窗口，那条私信行仍旧是未读，直到点开详情页
  （或「全部已读」）。回复不等于读过——正文全文只有详情页给。
- **后台那只私信表的两条查询没有索引**：列表按 `created_at` 排序、按日期下钻、正文用
  `body__icontains` 搜——`DirectMessage` 上一条索引都没有，所以都是全表扫描。
  社团规模下无感，**表真长大了要补的是一条 `("-created_at", "-pk")` 索引**，
  正文搜索则要另想办法（`icontains` 用不上 btree）。
- **私信没有审计底账**：后台那只表只读、也不写审计。出了「谁给谁发过」的争议，后台能看的是
  **现存的行**——收信人一删，那一行连同通知一起没了。要真的留痕就得写审计，那是另一条路。
- **浮动窗要脚本才弹**：没有脚本时那几个入口是普通链接，落到 `direct_compose` 整页表单——
  功能不缺，少的是弹窗这一层观感。
- **`Message` 的六个引用没有组合约束**：哪一类消息挂哪个引用是 `services.py` 写入函数的责任。
  绕过 services 直接建行能造出渲染不出来或语义错乱的消息。
- **`mark_all_read` 的返回计数**并发下可能多报（回执被 `ignore_conflicts` 挡掉，但计数已经算进去了）。
  这个数只用于日志，不影响页面。
- **`list.html` 今天只服务公开列表**：它带 `detail_namespace` / `detail_name` 两个参数、范围列直接写
  `{{ notice.scope }}`、不写已读回执——把成员侧的通知接进这一页会同时丢掉回执与范围口径。
- **已读回执没有清理入口**：只随通知／账号级联删除，没有「清理 N 天前的回执」这类命令。

## 4. 由来

- **为什么未读要现算**：可见通知 − 已读回执（`NoticeRead`），不物化副本——发布人删通知，成员侧自然
  消失，回执随 CASCADE 清掉，不留孤儿。
- **为什么私信的正文单开一张表**：消息行的规矩是「只存结构化引用与状态，可显示字段现取现算」——
  私信的正文恰恰没有别的家，别的 kind 的来源（帖子、评论、申请、轮次）都另有主人，私信没有。
  两条路：给 `Message` 加一列正文（那一列的规矩就破了，且将来每种「自带正文」的消息都要挤在这一列上），
  或者让正文自己也当一次「来源」。选了后者：「来源删除即级联删行」这条口径一个字都不用改。
- **为什么私信不写审计**：不写是决定，不是漏做——只追加的表配私人往来，代价是永久留痕。
- **为什么后台只给一只只读的表**：成员之间的事，后台的用途是「出了事能查」，不是「替成员管理」。
  所以**连删除也关掉**——删一条私信会连收信人「我的消息」里那一行一起带走（外键 `CASCADE`），
  那是在动成员自己那一页，不是运维的便利。这是唯一因为「有人要查」而破的口子，破得尽量小。
- **为什么「读完」不改消息的存亡**：已读与存在是两件事。删掉一条私信是收信人的动作（他不想再看见），
  与「读过」无关；反过来，读过就消失会让人再也找不到对方说过的话。
- **为什么回信也是一种普通私信**：回复不建新类型、不建会话表——它就是把收件人与发信人对调再发一条。
  于是未读、计数、提醒、删除全都复用同一条路。
- **为什么撤回了「登录 flash 与成员中心待办卡片」**：同一个数字不该有两处口径；未读统一由
  「我的消息」的提醒条报出。任务类消息跟着任务生命周期走（交掉／被释放／被改派即撤），历史归评审页。
