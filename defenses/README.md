# defenses 模块

> 线下模拟答辩：项目组发起一条**申请**，评审侧在「线下答辩」排期表里讨论时间与地点，
> 申请关闭后进入「已确定」并转为只读。申请绑定一个项目组，正文不超过 500 字；
> 讨论模仿 issue 的评论流，申请人改正文时自动留一条修改记录。
> 它不做评审轮次与结论（`reviews`），不判断「谁能进评审页」（`reviews.permissions`），
> 不判断「谁能管这个组」（`projects.permissions`），也不写消息的渲染与已读（`notices`）。
>
> **实名例外**：线下答辩的讨论是实名协调渠道，评论显示作者真实姓名（包括评审人）；
> 这是对评审模块「对项目组匿名」口径的**刻意例外**。别把评审意见、结论或评审回复
> 搬进这里——那些内容仍按评审模块的匿名规则处理。

**什么时候看**：改答辩申请的字段、状态、发起／评论／关闭的规则，或动排期页与详情页的时候。

---

## 1. 明确不做什么

| 不做 | 落在哪 |
|---|---|
| 「谁能进评审页」 | `reviews.permissions.can_open_queue`。排期表与「线下答辩」入口取同一个判据，本模块不另定义「谁算评审」 |
| 「谁能管这个项目组」 | `projects.permissions.can_manage_group`。发起申请只委托它，不重写「联系人／管理员」 |
| 消息的写入、渲染与已读 | `notices`（`notify_defense_request`、`selectors._defense_request_content`）。本模块只在创建时调用 |
| 评审轮次、任务、结论与归档 | `reviews`。线下答辩不是一轮送审，失败／改期也不需要评审结论 |
| 项目资料本体 | `projects.ProjectGroup.materials` |
| 用户可见文案 | 模板与服务层抛出的领域异常；修改记录那句话**不进数据库**，见 §2 |
| 后台的增改删 | 后台只有只读视图（`admin.py`）；成员侧才是写入口 |

## 2. 必须成立的断言

- **申请绑定一个项目组，申请人在创建时冻结**：`applicant` 是 `PROTECT` 外键。项目组
  之后转让联系人**不会**把申请转给新联系人——写申请的人继续是能改正文、能关闭的人。
  需要换人时，由新的项目组联系人另发一条申请。
- **状态只有两个，唯一写入点是 `services.close_request`**：`OPEN`（安排中）→
  `CLOSED`（已确定），没有反向。关闭在 `select_for_update()` 锁住申请行之后复查，
  所以「同时有人关闭、有人还在改／评论」不会留下半个状态。
- **「能看」不等于「能评论／能改／能关」**：当前联系人能在组管理页看到本组申请并
  打开详情（否则那一列链接会点出 403），但**评论只给三类评审资格、管理员与申请人**；
  改正文只给申请人；关闭只给申请人或管理员。四件事各有各的判据，模板隐藏入口不是
  边界，服务层与视图都会再判一次。
- **评论实名是刻意的例外**：评论区显示 `author.profile.full_name`（没有姓名时回落
  账号），评审人也在内。它与 `reviews` 的匿名口径相反，理由见 §4；**不要**为了
  「统一」把这里改成中性标签，也不要在这条线上讨论评审结论。
- **关闭即只读**：`can_edit_request` / `can_comment` / `can_close_request` 都以
  `is_open` 为前提；模板据此不渲染表单，服务层在行锁内再判一次。**只隐藏表单不是
  安全边界**。
- **修改记录只在正文真的变了时写一条**：`DefenseComment(kind=EDIT)` 的 `body` 永远
  为空。那句「申请者修改了答辩申请」写在模板里，跟着界面语言走；**不要把中文句子
  存进 `body`**，否则英文界面会显示中文，且同一条记录以后没法改措辞。
- **创建消息的收件人是创建那一刻的资格快照**：当前 `is_reviewer` /
  `is_preliminary_reviewer` / `is_super_reviewer` 任一为真的人各一条（`distinct`，
  三种资格都有也只收一条）。**管理员没有评审资格就不在收件人里**；申请人若也持有
  资格，同样会收到一条——那对他是「申请已创建」的回执。消息行不存标题与状态，
  关闭后说明列会跟着变成「已确定」。
- **两个列表是分开的查询，都按创建时间倒序**：`selectors.open_requests()` 与
  `closed_requests()` 各自过滤状态；页面上的「安排中 / 已确定」就是这两个查询，
  不靠模板再筛。
- **双击提交在短窗口内是幂等的**：同组、同申请人、同正文在
  `CREATE_IDEMPOTENCY_WINDOW`（10 秒）内只留一条申请，不重复发消息；有意再发一条
  请改正文或等窗口过去。
- **关闭是幂等的，过期页面不报 403**：对已经关闭的申请再次提交关闭／修改／评论，
  给一句提示并回到详情；403 只留给真正没有资格的人。真正的状态边界仍在服务层的
  行锁内复查。
- **评论不通知任何人**：本轮只有「创建」会产生站内消息；评论与关闭都不写。这是
  刻意的边界——排期讨论在页面里看，不把每条评论变成一封站内信。
- **审计 action 固定**：`defenses.request.create` / `defenses.request.update` /
  `defenses.comment.create` / `defenses.request.close`。发布后不再改名。

## 3. 已知限制 / 当前不支持

- **同一项目组可以同时有多条「安排中」的申请**：没有唯一约束。需要重开时不必先关闭
  旧的；页面按时间列出全部，由人自己分辨。若将来要求「一组同时只有一条」，要加的是
  部分唯一约束 + 服务层翻译，不是页面过滤。
- **发起入口只在项目组管理页**：也就只有该组联系人与管理员能发起；普通组员、评审人
  不能替一个组发起。排期表只负责看与讨论。
- **申请人失去评审资格、也不再是联系人后，仍能打开自己那条详情的直接地址，但进不了
  排期表**：`can_view_request` 为申请人留了一支，`can_access_schedule` 没有。这是
  「谁能进评审页」与「谁拥有这条申请」两个口径的刻意分离。当前联系人同样能看本组
  申请，但这条不延伸到评论、修改或关闭。
- **关闭后不能再评论**：详情页只保留最终正文与完整讨论。需要继续讨论就另发一条申请。
- **评论永久实名**：关闭后历史仍显示姓名；删除申请会连评论一起带走（后台已禁删）。
  这是实名协调的代价，发起前请知悉。
- **评论不能编辑或删除**：与「评论发表后不能修改」的页面提示一致；没有软删除。
- **没有分页、搜索与筛选**：两个列表一次取全。社团规模下无感，量大了要补分页。
- **没有「撤回」创建消息**：申请关闭后，收件人「我的消息」里那条行仍在，点进去看到
  的就是只读的已确定详情（说明列也已变成「已确定」）。这是现状，不是漏写。
- **创建消息的收件人快照不按账号状态过滤**：与 `notices.notify_create_request` 同一
  口径——被停用的账号若仍持有资格，也会收到一行站内消息。
- **`closed_by` / `closed_at` 的一致性只由服务层保证**：模型没有约束要求「已确定必有
  关闭人」，绕过 `close_request` 直接写状态可以造出坏行。
- **正文上限只在表单与服务层把关**：PostgreSQL 的 `text` 不执行 `max_length`，绕过
  两者直接建行能存进超长正文。

## 4. 由来

- **为什么单开一个 app**：它同时被项目组管理页（发起）与评审页（排期）使用，但既不
  属于「项目组资料」也不属于「一轮送审」；放进任一边都会让那边多背一个状态机。
  独立之后依赖方向清楚：模型指向 `projects`、消息走 `notices`，权限只在函数体内问
  `projects` / `reviews`。
- **为什么修改记录不存句子**：界面上它是一条评论，但它表达的是「发生过一次编辑」，
  不是谁说了什么。把文案留给模板，英文界面才对；也让「每次修改自动发一条」不必在
  数据库里积累同一条中文句子的无数副本。
- **为什么关闭是终态而不是可重开**：排期一旦确定，后续再改会让已经按旧时间安排的人
  落空。要新时间就另发一条，历史留在旧申请里。
- **为什么线下答辩评论实名**：这是一条协调渠道——联系人要知道「谁能来、谁不能来」，
  匿名标签会让「我能到」失去意义。它与评审意见的匿名规则是两件事：评审意见评价的
  是项目资料，线下答辩协调的是时间与地点。例外只开在 `defenses` 的讨论区，没有
  扩大到评审页、评审回复或归档件。
